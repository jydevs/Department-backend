# Fase 4 — Carrito, checkout, pedidos y pagos (contrato)

Reglas globales: las de fases 1–3 (TS estricto sin `any`, Zod DTOs, `AppException`, `TransactionService.run`, `AuditService.record(..., manager)` en escrituras admin, `Clock`, `IdParamDto`,
permisos por endpoint, SQL parametrizado, sin tests, DTO de respuesta explícitos, dinero = `bigint` COP con `moneyTransformer` y `number` entero en el dominio).
Compra como INVITADO (sin cuenta); en la Fase 5 se enlaza con clientes por email. Precios y totales SIEMPRE se recalculan en el servidor: el cliente jamás envía precios.

## Estados
- `Order.status`: `pending` (esperando pago, con stock reservado) · `open` (pagado, en gestión) · `completed` (totalmente enviado) · `cancelled` · `expired` (no pagó a tiempo).
- `Order.paymentStatus`: `pending|paid|failed|partially_refunded|refunded`. `Order.fulfillmentStatus`: `unfulfilled|partial|fulfilled`.
- Transiciones válidas: pending→open (pago aprobado) · pending→cancelled|expired (libera reserva) · open→completed (todo enviado) · open→cancelled (con `restock` opcional; si estaba pagado exige registrar reembolso o marcar `refundPending`).
- Numeración: secuencia Postgres `order_number_seq` (inicio 1001); `orderNumber` int único, mostrado `#1001`.

- `OrderLine`: orderId FK cascade, variantId uuid (SIN FK: la variante puede desactivarse), productId uuid, sku null, title (producto), variantTitle, imageUrl null, unitPrice bigint, quantity int, lineTotal bigint, fulfilledQuantity int default 0, refundedQuantity int default 0.

## Pricing (C2) — `src/commerce/pricing/**` (exporta `PricingModule` con `PricingService`)
`quote(input: { lines: {variantId; quantity}[]; discountCode?: string | null; shippingRateId?: string | null; department?: string | null; email?: string | null }, manager?: EntityManager): Promise<Quote>`
`Quote = { currency:'COP'; lines: QuoteLine[]; subtotal; discountTotal; discount: {code; type; amount}|null; shippingTotal; shippingRate: {id; name}|null; taxTotal; total; warnings: {code; message; variantId?}[] }`,
`QuoteLine = { variantId; productId; productTitle; variantTitle; sku|null; imageUrl|null; unitPrice; compareAtPrice|null; quantity; lineTotal; available: boolean; maxQuantity: number|null }`.
- Precio = `variants.price` actual; variante inactiva/producto no activo/borrado => línea inválida (warning `VARIANT_UNAVAILABLE`) y el checkout la rechaza.
- Descuentos: valida activo, ventana de fechas, usageLimit, minSubtotal, oncePerEmail (si hay email); percent sobre subtotal (redondeo half-up entero), fixed nunca mayor que subtotal, free_shipping pone envío en 0. Códigos case-insensitive. Error específico `DISCOUNT_INVALID` con `reason`.
- Envío: tarifa por `shippingRateId` que pertenezca a una zona activa que cubra `department` (o `*`); `freeOverSubtotal` aplica sobre subtotal ya descontado; sin tarifa => shippingTotal 0 y `shippingRate:null`.
- Impuestos: con `pricesIncludeTax=true` (Colombia) `taxTotal = round(base * rate / (100 + rate))` donde base = subtotal - discountTotal + shippingTotal, y NO se suma al total; si es false se suma. Redondeo half-up entero.
- Determinista y puro sobre la BD (sin efectos), un solo viaje por tabla (sin N+1).
Además C2 implementa: **Carrito storefront** `/storefront/carts` (crear → `{ id, token, expiresAt }`; el token opaco de 32 bytes base64url se devuelve UNA vez y se guarda su sha256; cabecera `X-Cart-Token` obligatoria en las demás rutas, comparación timing-safe, 404 (no 403) si no coincide; `GET /storefront/carts/:id` devuelve carrito + Quote; `POST :id/lines {variantId, quantity}` (suma si existe; máx 50 líneas y 20 unidades por línea; valida variante vendible y stock disponible — 409 `INSUFFICIENT_STOCK` con `available`), `PATCH :id/lines/:variantId {quantity}` (0 elimina), `DELETE :id/lines/:variantId`, `PUT :id/discount {code|null}`, `DELETE :id`; expira 30 días tras la última actividad (se renueva en cada escritura); throttle `@Throttle` 60/min crear y 120/min resto); `GET /storefront/shipping-rates?department=&cartId=` con `X-Cart-Token`; **admin** `/admin/shipping/zones|rates` CRUD (`shipping:read|write`), `/admin/discounts` CRUD + `GET :id/redemptions` (`discounts:read|write`), `GET/PUT /admin/taxes` (`settings:write` para PUT, `settings:read`… usa `shipping:read` para GET), auditoría en cada escritura; limpieza de carritos expirados (scheduler 1 h, borra en lotes de 500).

## Checkout, pagos y ciclo de vida (C3) — `src/commerce/checkout/**`, `src/commerce/payments/**`, `src/commerce/orders/orders-lifecycle.service.ts`
- `POST /storefront/checkouts` (header `Idempotency-Key` OBLIGATORIO 8..120 caracteres; `X-Cart-Token`; body `{ cartId, email, phone?, shippingAddress, billingAddress?, shippingRateId, discountCode?, customerNote? }`; throttle 10/min):
  1. En UNA transacción: bloquea idempotencia (`INSERT ... ON CONFLICT DO NOTHING` + `SELECT ... FOR UPDATE`); misma key + mismo hash => devuelve la respuesta guardada; misma key con cuerpo distinto => 422 `IDEMPOTENCY_KEY_REUSED`; en curso => 409 `IDEMPOTENCY_IN_PROGRESS`.
  2. `PricingService.quote` con todo el detalle; rechaza si hay líneas no disponibles o warnings bloqueantes; carrito vacío => 400 `CART_EMPTY`; carrito ya convertido => 409.
  3. `InventoryService.reserve(items, manager)` (409 `INSUFFICIENT_STOCK` con details), crea `Order` `pending` con `reservedUntil = now + 30 min`, OrderLines con snapshot, `Payment` `pending`, `OrderEvent` `order.created`, `DiscountRedemption` + incremento atómico `UPDATE discounts SET used_count = used_count + 1 WHERE id = $1 AND (usage_limit IS NULL OR used_count < usage_limit)` verificando filas, marca el carrito `convertedOrderId`.
  4. Respuesta `{ orderNumber, orderId, accessToken (una sola vez), total, currency, payment: PaymentInstructions }` donde `PaymentInstructions = { provider: 'wompi'|'mock'; reference; amountInCents (=total*100); currency; publicKey?; signatureIntegrity?; redirectUrl?; checkoutUrl? }`.
- **PaymentProvider** (interfaz, token de inyección): `createPayment(order): PaymentInstructions`, `verifyWebhook(headers, rawBody): VerifiedEvent | null`, `parseTransaction(event): { eventId; reference; providerTransactionId; status: 'approved'|'declined'|'voided'|'error'|'pending'; amountInCents; currency; method? }`. Implementaciones: **WompiProvider** (firma de integridad `SHA256(reference + amountInCents + currency + WOMPI_INTEGRITY_SECRET)` en hex; verificación de eventos: checksum = SHA256(concatenación de los valores de `signature.properties` extraídos de `data` + `timestamp` + `WOMPI_EVENTS_SECRET`), comparación timing-safe con `signature.checksum`; ignora eventos que no sean `transaction.updated`; URL base `WOMPI_API_URL` por defecto sandbox `https://sandbox.wompi.co/v1`; rechaza si falta un secreto) y **MockProvider** (dev/test: `PAYMENT_PROVIDER=mock`, instrucciones con `checkoutUrl` ficticio; los eventos se firman con HMAC usando `WOMPI_EVENTS_SECRET` o un secreto de dev). `PAYMENT_PROVIDER` por defecto `mock` fuera de producción y OBLIGATORIAMENTE `wompi` en producción (validación de env).
- `POST /webhooks/wompi` (fuera de `/api/v1`, `@Public()`, `@SkipThrottle()`, usa `req.rawBody`; firma inválida => 401 sin detalle; evento válido siempre responde 200 salvo error transitorio => 500 para que reintenten): en transacción `INSERT INTO processed_events ... ON CONFLICT DO NOTHING` (si ya existía => 200 no-op); localiza el pedido por `reference` con `SELECT ... FOR UPDATE`; VERIFICA que monto y moneda coinciden con el pedido (si no => registra `OrderEvent payment.mismatch`, no cambia estado, 200); `approved` sobre pedido `pending` => `markPaid`; `approved` sobre `expired|cancelled` => registra `payment.late_approval` y marca `refundPending` en el pedido (requiere acción del admin; NO reabre); `declined|voided|error` sobre `pending` => cancela y libera reserva. Siempre idempotente.
- `OrdersLifecycleService` (exportado): `markPaid(orderId, payment: { providerTransactionId?; method?; manual?: boolean }, manager, actor?)` (pending→open, paymentStatus paid, `InventoryService.commit`, evento, `paidAt`), `cancel(orderId, opts: { reason: string; restock: boolean; actor? }, manager)` (pending: release; open sin envíos: restock opcional con `InventoryService.restock`; con envíos parciales 409 `ORDER_HAS_FULFILLMENTS`), `expirePending(now: Date, batch: number): Promise<number>` y un `OrdersScheduler` cada 60 s (`FOR UPDATE SKIP LOCKED`, pedidos `pending` con `reservedUntil <= now`, libera reserva, `expired`). Añade a `InventoryService` (archivo `src/inventory/inventory.service.ts`, ÚNICO cambio permitido fuera de tu carpeta) el método `restock(items: {variantId; quantity}[], manager: EntityManager, reason: 'returned'|'correction'): Promise<void>` que suma `on_hand` en la ubicación default y registra `InventoryAdjustment` (mismo patrón de bloqueo que `commit`).
- `GET /storefront/orders/:orderNumber?token=<accessToken>` (público, comparación timing-safe con hash, 404 si no coincide) → estado del pedido para la página de gracias (líneas, totales, estados, envío/tracking; sin datos internos ni de otros).
- Solo en desarrollo con `PAYMENT_PROVIDER=mock`: `POST /storefront/dev/mock-payment { reference, status }` que sintetiza un evento firmado y lo procesa por la misma ruta interna del webhook (404 en cualquier otro caso).
- Env nuevo (validado en `src/config/env.ts` por el orquestador): `PAYMENT_PROVIDER`, `WOMPI_PUBLIC_KEY`, `WOMPI_INTEGRITY_SECRET`, `WOMPI_EVENTS_SECRET` (ya existe), `WOMPI_API_URL`, `ORDER_RESERVATION_MINUTES` (30).

## Pedidos admin (C4) — `src/commerce/orders/**` (excepto `orders-lifecycle.service.ts`)
Permisos `orders:read` / `orders:write` (el orquestador añade `shipping:*`, `discounts:read`, `settings:read`).
- `GET /admin/orders` (`PageQueryDto` + filtros `status`, `paymentStatus`, `fulfillmentStatus`, `q` [número exacto, email o nombre parcial escapado], `from`, `to`, `tag`); resumen con número, fecha, cliente, total, estados, nº de artículos; sin N+1.
- `GET /admin/orders/:id` detalle completo (líneas con `fulfilledQuantity/refundedQuantity`, direcciones, pagos, envíos, reembolsos, evento).
- `PATCH /admin/orders/:id` (`internalNote`, `tags`, email/teléfono y dirección de envío solo si `unfulfilled`; `version` para bloqueo optimista), `POST :id/notes` (nota de línea de tiempo), `GET :id/timeline` (`OrderEvent` paginado).
- `POST :id/cancel {reason, restock}` y `POST :id/mark-paid {reference?, note?}` delegan en `OrdersLifecycleService` con auditoría; `POST :id/fulfillments {lines:[{orderLineId, quantity}], carrier?, trackingNumber?, trackingUrl? (https), notifyCustomer?}` (solo pedidos `open`; valida cantidad pendiente por línea; actualiza `fulfilledQuantity`, `fulfillmentStatus` y `completed` cuando todo esté enviado; evento), `POST :id/fulfillments/:fid/cancel` (revierte cantidades),
  `POST :id/refunds {amount, reason?, lines?: [{orderLineId, quantity}], restock: boolean}` (solo `open|completed` pagados; `amount` ≤ total pagado − ya reembolsado; con `restock` suma stock de las líneas indicadas vía `InventoryService.restock`; actualiza `totalRefunded`, `refundedQuantity`, `paymentStatus` partially_refunded/refunded; `providerStatus:'manual'` porque el reembolso real se hace en el panel de Wompi — dejar constancia), todo transaccional con `SELECT ... FOR UPDATE` del pedido.
- Auditoría (`AuditService`) + `OrderEvent` en cada acción.

## Criterio de aceptación (smoke del orquestador)
Crear carrito → añadir línea → cotizar con descuento y envío → checkout con Idempotency-Key (repetirlo devuelve lo mismo; con cuerpo distinto 422) → stock reservado (available baja) → webhook mock aprobado con firma válida (firma inválida 401; repetido no duplica) → pedido `open`/paid, stock comprometido → admin crea fulfillment con tracking → pedido `completed` → reembolso parcial con restock → cancelación de un pedido pendiente libera la reserva → pedido que expira libera reserva → aprobación tardía queda marcada `refundPending` → analyst 403 en refunds → descuento con `usageLimit=1` no se puede usar dos veces en paralelo.
